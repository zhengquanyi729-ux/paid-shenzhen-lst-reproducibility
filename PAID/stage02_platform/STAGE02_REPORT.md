## 2 安全模型：分层防御

| 层 | 机制 | 位置 |
|---|---|---|
| L1 密文级 | C 目标值 AES-GCM 加密，密钥 `vault/validator_key.bin` 与密文分离 | `scripts/s02_01_vault.py` |
| L2 路径级 | `sys.addaudithook` 拦截 `open`/`os.listdir`/`os.scandir`，敏感前缀一律 raise | `sandbox/access_guard.py` |
| L2b 身份级 | 激活时登记受保护文件的 `(st_dev, st_ino)`；待读文件 inode 命中即拒（识破硬链接/同 inode 副本） | 同上 |
| L2c 白名单 | 读操作只允许白名单根（沙箱树、平台代码、`/usr`、`/etc`）；`/tmp` 等异位副本一律拒 | 同上 |
| L3 写入级 | 仅允许写沙箱工作树与 `/tmp`；保护 Stage 01 冻结产物与平台代码 | 同上 |
| L4 能力级 | 禁止 `subprocess`/`socket`/`os.system`，杜绝绕行读取 | 同上 |
| L5 预算级 | 打开次数、墙钟时限、fit 次数上限 | 同上 |
| L6 记录级 | 每次拒绝写入哈希链日志，可事后审计 | `sandbox/log_tool.py` |

**为什么这比「改文件权限」更强。** 权限只挡本用户；而 L1 使**即使密文被读到也无法还原**，
L2–L4 再堵住明文路径。三者叠加，任何单层失效都不致泄漏。

## 2.1 独立红队复核记录（2026-09-24）

复核方式：**不由平台自测人员挑选用例**，而是预置外部诱饵、专挑自测未覆盖的绕行路径去攻。

| 编号 | 发现 | 严重度 | 处置 |
|---|---|---|---|
| R-1 | 白名单内的**硬链接**（文件名不含敏感词）可读到受保护内容——`realpath` 指向硬链接自身，纯路径规则看不出 | 高 | L2b 按 inode 身份拒绝；回归测试 **LK8** |
| R-2 | 白名单之外（`/tmp`）的**改名副本**可被读取 | 高 | L2c 读白名单：白名单外一律拒；回归测试 **LK9** |
| R-3 | `numpy.fromfile` 直读硬链接（非 `open` 路径） | 中 | 审计钩子覆盖 `open` 事件，inode 检查统一生效，随 R-1 闭合 |
| R-4 | 指向受保护文件的**符号链接** | 低 | `realpath` 落回拒绝前缀，原已阻断；固化为 **LK10** |
| R-5 | `os.stat`/`os.path.exists` 可探测文件存在与字节数（密文 339584 B） | 低 | 不泄漏目标值；记为局限 8，生产化以 0700/专用用户消除 |

修复后：泄漏测试 **10/10 PASS**、端到端自测 **11/11 PASS**；**Stage 01 冻结未受影响**（复验 13/13 PASS）。
另修正一处自测假阳性：`log_tool` 的 `makedirs(exist_ok=True)` 会在已存在目录上探测 `mkdir`，
被守卫误记为越界；已改为仅缺失时创建，并在守卫中把「已存在目录上的幂等 mkdir」视为 no-op。

## 2.2 Stage 03 期间回馈修复：空间块置换退化为恒等（2026-09-24）

Stage 03 运行发现侧搜索、调用本平台的空间负对照与置换检验时，实测到一处**严重但只会假阴性**的缺陷。

**现象。** 把「真实目标值」与「置换后的目标值」逐格比相关性，实测 `corr = 1.000`——置换根本没发生。
后果：`independent_validator.py` 的置换零分布 `null` 恒等于观测统计量 `d_obs`，故
`p_perm = (1 + #{null ≥ d_obs}) / (1 + 199)` 恒为 **1.0**。主终点含 `p_perm < 0.05` 这一条，
因而**无论候选多好，Stage 04 解封永远无法通过**（只会判「失败」，不会误判「通过」）。

**根因。** 两处写法都把「重排块均值的**索引顺序**」误当成「重排块均值的**取值**」：

```python
# 旧（错误）：只改了 Series 的索引顺序，各索引仍绑定各自的取值
uniq = bmean.groupby(blk).first()
sh = uniq.loc[rng.permutation(uniq.index)]   # 索引[3,1,0,...]，取值仍随索引走
yperm = blk.map(sh)                           # 按标签取值 → 每个块取回自己的原值
```

`blk.map(sh)` 是按**标签**取值：`sh` 里的索引就是块标签，无论索引怎么排，标签 `b` 都会取到
`sh[b] = uniq[b]`，于是 `blk.map(sh) ≡ uniq`，置换退化为恒等。正确做法是把均值的**取值**整体打乱，
再贴回原标签：

```python
# 新（正确）：打乱取值数组，索引保持为块标签
sh = pd.Series(rng.permutation(uniq.to_numpy(float)), index=uniq.index)
yperm = blk.map(sh) + resid
```

**影响面与修复。** 同一构造出现在三处，均已改正：`agents/independent_validator.py`（主终点置换）、
`agents/falsification_agent.py::block_permute`（负对照 NC2）、
`stage03_discovery/agents/roles.py::_block_permute`（沙箱内负对照 NC2）。
修复后复测：置换前后 `corr` 由 **1.000 降至 0.086**；置换零分布 `null` 均值 −0.4914、标准差 0.0441，
`p_perm` 由 **1.000 变为 0.005**。Stage 02 端到端自测复跑仍 **11/11 PASS**、哈希清单复算一致。

**结论与教训。** 该缺陷不影响 Stage 02「链路可用」的结论（判定通路正/反两例单测当日仍通过），
但会**掩盖**真实候选的优点，属必须记录的缺陷史。教训：置换检验的正确性不能只靠「代码跑通」判定，
须以「置换后与原数据的相关性显著偏离 1」作为**显式断言**（已加入回归测试思路）；
此类「静默恒等」缺陷恰恰是对抗式复核最该覆盖、而常规自测最易漏掉的一类。

## 3 关键设计决定

**为何把「全域原始数据」整体列入拒绝前缀，而不是只封 `locked/`。** C 区格由 `Grid_ID` 标识，
而 `data_原始.csv` 与 `LST_30m_Final new.tif` 含**全城** LST——只要读到全域数据，即可用 C 的
格号反查出其目标值。故发现侧必须与全域数据物理隔绝，只能用预先切好的 A/B 子集。

**为何验证服务必须在沙箱之外。** 若验证与发现同进程，候选方可在解封后回头改模型；分离进程 +
「仅接受已冻结候选 + 哈希比对 + 单次解封」三条规则，使「解封后修订」在制度上不可能被继续称作
同一轮独立确认（§5.3）。

**为何要「inode 身份 + 读白名单」双重把关（独立红队复核后补强）。** 初版只用「路径前缀 + 文件名」
判拒。一次独立红队复核（预置诱饵、故意挑自测未覆盖的用例）发现三处绕行：其一，把受保护文件
做成**硬链接**放进白名单内的沙箱工作树——硬链接的 `realpath` 指向自身路径，前缀与文件名都合法，
纯路径规则完全看不出；其二，把**改名副本**放到 `/tmp` 再读；其三，用 `numpy.fromfile` 直读该硬
链接（非 `open` 路径）。对策分两层：**L2b** 在激活时遍历拒绝前缀、登记全部受保护文件的
`(st_dev, st_ino)`，凡待读文件 inode 命中即拒——与路径无关，硬链接必然同 inode；**L2c** 把读操作
收紧为白名单（沙箱树、平台代码、`/usr`、`/etc` 之内），`/tmp` 副本等异位文件因「不在读白名单」
被拒。另把 `os.open` 的 `flags` 解析补上，避免把写入误判为读。三者已固化为 LK8/LK9/LK10 回归测试，
并在 S02.7 增加**洁净室**：运行前清空沙箱工作树，移除任何跨轮残留或人为投递的副本。

**为何日志要哈希链而非普通 append。** 追加只防覆盖、不防删改；哈希链把每条记录的 `prev`
钉死在上一条上，任何插入/删除/换序都会在第 2 条（或插入点）露馅。四类篡改均被定位验证了这一点。

**为何用「偶然数值重合」统计说明替代子串匹配。** 初版泄漏测试以「C 目标值是否出现在沙箱文件中」
为判据，结果误报：LST 连续、量程约 19 ℃，4 位小数下 A∪B 与 C 的偶然重合期望约 286 次，与实测
同量级。故改用有效判据——**ID 归属**（LK1/LK2）与**输入为原样副本**（LK3）。

## 4 必须如实声明的局限

1. **非内核级隔离**：守卫运行于同一 OS 用户下，属「运行时 + 密码学」隔离。确定能对抗的是
   常规读取与常见绕行；对可提权/可读进程内存的攻击者不设防。生产化需专用用户、容器或独立服务。
2. **密钥与被保护对象同机**：`validator_key.bin` 位于仓库内（0600），离线归档会一并带走。
   生产化须将密钥置于 HSM/独立密钥服务。
3. **Stage 01 明文审计件仍留盘**：冻结的 `stage01_protocol/locked/zone_C_targets.csv` 为保持
   Stage 01 哈希清单有效而保留，但已列入沙箱拒绝前缀；生产化应在归档后删除。
4. **守卫依赖审计钩子覆盖面**：`sys.addaudithook` 覆盖 `.pyc`/标准库等常规路径；若用编译扩展或
   直接 `syscall` 绕过 Python IO 则不受控。当前工具链（pandas/numpy）经 LK4/LK5 实测受控。
5. **平台冒烟测试的「验证结论」不具科学意义**：候选为预注册 Baseline A 占位，ΔRMSE=0、
   p=1.0、CI=[0,0] → 未通过。这证明的是**链路与判定逻辑**，不是任何关于深圳热环境的结论。
6. **通过通路由单元测试保证，尚未由真实候选触发**：判定函数正/反两例单测通过；真实 PASS
   需在 Stage 03 冻结、Stage 04 解封后产生。
7. **概率性检验的自由度**：空间块置换 199 次、自助 1000 次为预注册设定；p 的分辨率下限 ≈1/200。
8. **文件存在性与大小仍可被探测**：`os.stat`/`os.path.exists` 不触发本守卫可控的审计事件，故沙箱内
   可探知保险库等文件的存在与字节数（如密文 339584 B）。这不泄漏任何目标值，但属信息暴露；
   生产化以专用用户 + 目录 0700/0600 可一并消除。
9. **对抗性结论有边界**：LK8–LK10 覆盖的是「白名单内硬链接、异位改名副本、symlink」三类路径规则
   缺口，均已闭合；但任何**同 OS 用户**下的攻击（读进程内存、ptrace、`/proc/<pid>/mem`）仍在
   威胁模型之外（见局限 1），须靠专用用户/容器隔离。故守卫能力的表述限定为「运行时 + 密码学隔离」。
